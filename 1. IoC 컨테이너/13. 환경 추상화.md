# 환경 추상화

[`Environment`](https://docs.spring.io/spring-framework/docs/6.1.11/javadoc-api/org/springframework/core/env/Environment.html) 인터페이스는 애플리케이션 환경의 두 가지 주요 측면인 프로파일과 속성을 모델링하는 컨테이너에 통합된 추상화이다.

프로파일은 지정된 프로파일이 활성화된 경우에만 컨테이너에 등록되는 명명된 논리적 빈 정의 그룹이다. 빈은 XML로 정의하든 어노테이션으로 정의하든 프로파일에 할당될 수 있다. 프로파일과 관련된 `Environment` 객체의 역할은 현재 활성화된 프로파일(있는 경우)과 기본적으로 활성화되어야 하는 프로파일(있는 경우)을 결정하는 것이다.

속성은 거의 모든 애플리케이션에서 중요한 역할을 하며 속성 파일, JVM 시스템 속성, 시스템 환경 변수, JNDI, 서블릿 컨텍스트 매개변수, 애드혹 `Properties` 객체, `Map` 객체 등 다양한 소스에서 비롯될 수 있다. 속성과 관련된 `Environment` 객체의 역할은 사용자에게 속성 소스를 설정하고 이로부터 속성을 확인할 수 있는 편리한 서비스 인터페이스를 제공하는 것이다.

## 빈 정의 프로파일

빈 정의 프로파일은 서로 다른 환경에서 다양한 빈을 등록할 수 있도록 핵심 컨테이너에 메커니즘을 제공한다. "환경"이라는 단어는 사용자마다 다른 의미를 가질 수 있으며, 이 기능은 다음과 같은 많은 사용 사례에 도움이 될 수 있다.

- 개발 시에는 인메모리 데이터 소스를 대상으로 작업하고, QA 또는 프로덕션 시에는 JNDI에서 동일한 데이터 소스를 조회한다.
- 애플리케이션을 성능 환경에 배포할 때만 모니터링 인프라를 등록한다.
- 고객 A와 고객 B 배포를 위한 사용자 정의된 빈 구현을 등록한다.

`DataSource`가 필요한 실제 애플리케이션의 첫 번째 사용 사례를 생각해 보라. 테스트 환경에서는 설정이 다음과 비슷할 수 있다.

```java
@Bean
public DataSource dataSource() {
    return new EmbeddedDatabaseBuilder()
	.setType(EmbeddedDatabaseType.HSQL)
	.addScript("my-schema.sql")
	.addScript("my-test-data.sql")
	.build();
}
```

이제 애플리케이션의 데이터 소스가 프로덕션 애플리케이션 서버의 JNDI 디렉터리에 등록되어 있다고 가정하여 이 애플리케이션을 QA 또는 프로덕션 환경에 배포하는 방법을 살펴보자. 이제 `DataSource` 빈은 다음 목록과 같이 보인다.

```java
@Bean(destroyMethod = "")
public DataSource dataSource() throws Exception {
    Context ctx = new InitialContext();
    return (DataSource) ctx.lookup("java:comp/env/jdbc/datasource");
}
```

문제는 현재 환경에 따라 이 두 가지 변형을 어떻게 전환할 것인가 이다. 시간이 지남에 따라 스프링 사용자들은 이를 위해 여러 가지 방법을 고안해왔는데, 일반적으로 환경 변수 값에 따라 올바른 설정 파일 경로로 확인되는 `${placeholder}` 토큰이 포함된 XML `<import/>` 문과 시스템 환경 변수의 조합에 의존해왔다. 빈 정의 프로파일은 이 문제에 대한 해결책을 제공하는 핵심 컨테이너 기능이다.

앞의 환경별 빈 정의 예시에서 보여준 사용 사례를 일반화하면, 특정 상황에서는 특정 빈 정의를 등록하고 다른 상황에서는 등록하지 않아야 할 필요가 생긴다. 상황 A에서는 특정 프로파일의 빈 정의를 등록하고 상황 B에서는 다른 프로파일을 등록하고 싶다고 말할 수 있다. 이러한 요구를 반영하도록 설정을 업데이트하는 것부터 시작한다.

### `@Profile` 사용하기

[`@Profile`](https://docs.spring.io/spring-framework/docs/6.1.11/javadoc-api/org/springframework/context/annotation/Profile.html) 어노테이션을 사용하면 하나 이상의 지정된 프로파일이 활성화되어 있을 때 컴포넌트가 등록할 수 있음을 나타낼 수 있다. 앞의 예시를 사용하면 다음과 같이 `dataSource` 설정을 다시 작성할 수 있다.

```java
@Configuration
@Profile("development")
public class StandaloneDataConfig {

    @Bean
    public DataSource dataSource() {
	return new EmbeddedDatabaseBuilder()
	    .setType(EmbeddedDatabaseType.HSQL)
	    .addScript("classpath:com/bank/config/sql/schema.sql")
	    .addScript("classpath:com/bank/config/sql/test-data.sql")
	    .build();
    }
}
```

```java
@Configuration
@Profile("production")
public class JndiDataConfig {

    @Bean(destroyMethod = "") ❶
    public DataSource dataSource() throws Exception {
	Context ctx = new InitialContext();
	return (DataSource) ctx.lookup("java:comp/env/jdbc/datasource");
    }
}
```

❶ `@Bean(destroyMethod = "")`은 기본 소멸 메서드 추론을 비활성화한다.

> ### 주의
> 
> 앞서 언급했듯이, `@Bean` 메서드를 사용하면 일반적으로 스프링의 `JndiTemplate`/`JndiLocatorDelegate` 헬퍼를 사용하거나 앞서 설명한 `JndiObjectFactoryBean` 변형이 아닌, 반환 타입을 `FactoryBean` 타입으로 선언해야 하는 `JndiInitialContext` 사용법을 통해 프로그래밍 방식의 JNDI 조회를 선택한다.

프로파일 문자열에는 간단한 프로파일 이름(예: `production`) 또는 프로파일 표현식이 포함될 수 있다. 프로파일 표현식을 사용하면 보다 복잡한 프로파일 로직을 표현할 수 있다(예: `production & us-east`). 프로파일 표현식에서 지원되는 연산자는 다음과 같다.

- `!`: 프로파일의 논리적 `NOT`
- `&`: 프로파일의 논리적 `AND`
- `|`: 프로파일의 논리적 `OR`

> ### 주의
> 
> 괄호를 사용하지 않고 `&` 및 `|` 연산자를 혼합할 수 없다. 예를 들어, `production & us-east | eu-central`은 올바른 표현이 아니다. `production & (us-east | eu-central)`로 표현해야 한다.

`@Profile`을 메타 어노테이션으로 사용하여 사용자 정의로 작성된 어노테이션을 만들 수 있다. 다음 예에서는 `@Profile("production")`을 대신하여 사용할 수 있는 사용자 정의 `@Production` 어노테이션을 정의한다.

```java
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Profile("production")
public @interface Production {
}
```

> ### 팁
> 
> `@Configuration` 클래스가 `@Profile`로 표시된 경우, 지정된 프로파일 중 하나 이상이 활성화되어 있지 않으면 해당 클래스와 연결된 모든 `@Bean` 메서드와 `@Import` 어노테이션이 무시된다. `@Component` 또는 `@Configuration` 클래스가 `@Profile({"p1", "p2"})`로 표시된 경우, 해당 클래스는 프로파일 'p1' 또는 'p2'가 활성화되지 않는 한 등록되거나 처리되지 않는다. 지정된 프로파일 앞에 NOT 연산자(`!`)가 붙으면 해당 프로파일이 활성화되지 않은 경우에만 어노테이션이 달린 요소가 등록된다. 예를 들어 `@Profile({"p1", "!p2"})`이 주어진 경우 프로파일 'p1'이 활성화되어 있거나 프로파일 'p2'가 활성화되지 않은 경우에만 등록이 이루어진다.

다음 예시에서 볼 수 있듯이, `@Profile`은 메서드 수준에서 선언하여 설정 클래스의 특정 빈(예: 특정 빈의 대체 변형)만 포함할 수도 있다.

```java
@Configuration
public class AppConfig {

    @Bean("dataSource")
    @Profile("development") ❶
    public DataSource standaloneDataSource() {
	return new EmbeddedDatabaseBuilder()
	    .setType(EmbeddedDatabaseType.HSQL)
	    .addScript("classpath:com/bank/config/sql/schema.sql")
	    .addScript("classpath:com/bank/config/sql/test-data.sql")
	    .build();
	}

    @Bean("dataSource")
    @Profile("production") ❷
    public DataSource jndiDataSource() throws Exception {
	Context ctx = new InitialContext();
	return (DataSource) ctx.lookup("java:comp/env/jdbc/datasource");
    }
}
```

❶ `standaloneDataSource` 메서드는 `development` 프로파일에서만 사용할 수 있다.
❷ `jndiDataSource` 메서드는 `production` 프로필에서만 사용할 수 있다.

> ### 주의
> 
> `@Bean` 메서드에 `@Profile`을 사용하면 특별한 시나리오가 적용될 수 있다. 동일한 자바 메서드 이름의 `@Bean` 메서드가 오버로드된 경우(생성자 오버로딩과 유사), 모든 오버로드된 메서드에 `@Profile` 조건이 일관되게 선언되어야 한다. 조건이 일관되지 않으면 오버로드된 메서드 중 첫 번째 선언의 조건만 중요하다. 따라서 `@Profile`을 사용하여 특정 인수 시그니처를 가진 오버로드된 메서드를 선택할 수는 없다. 동일한 빈에 대한 모든 팩토리 메서드 간의 해결은 생성 시 스프링의 생성자 해결 알고리즘을 따른다.
> 
> 프로파일 조건이 다른 대체 빈을 정의하려면 앞의 예에서와 같이 `@Bean` 이름 속성을 사용하여 동일한 빈 이름을 가리키는 고유한 자바 메서드 이름을 사용한다. 인수 시그니처가 모두 동일한 경우(예를 들어, 모든 변형이 인수가 없는 팩토리 메서드를 가지는 경우), 이는 유효한 자바 클래스에서 이러한 배열을 표현하는 유일한 방법이다(특정 이름과 인수 시그니처를 가진 메서드는 하나만 존재할 수 있기 때문이다).
