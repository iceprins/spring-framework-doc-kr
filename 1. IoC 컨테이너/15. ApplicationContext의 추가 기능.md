# ApplicationContext의 추가 기능

이 장의 소개에서 설명한 것처럼, `org.springframework.beans.factory` 패키지는 프로그래밍 방식을 포함하여 빈을 관리하고 조작하기 위한 기본 기능을 제공한다. `org.springframework.context` 패키지는 애플리케이션 프레임워크 지향적인 스타일로 추가 기능을 제공하기 위해 다른 인터페이스를 확장할 뿐만 아니라 `BeanFactory` 인터페이스를 확장하는 [`ApplicationContext`](https://docs.spring.io/spring-framework/docs/6.1.11/javadoc-api/org/springframework/context/ApplicationContext.html) 인터페이스를 추가한다. 많은 사람들이 `ApplicationContext`를 완전히 선언적인 방식으로 사용하며, 프로그래밍 방식으로 생성하지 않고 `ContextLoader`와 같은 지원 클래스에 의존하여 자카르타 EE 웹 애플리케이션의 일반적인 시작 과정의 일부로 `ApplicationContext`를 자동으로 인스턴스화한다.

보다 프레임워크 지향적인 스타일로 `BeanFactory` 기능을 향상시키기 위해 컨텍스트 패키지는 다음과 같은 기능도 제공한다.

- `MessageSource` 인터페이스를 통해 i18n 스타일의 메시지에 액세스한다.
- `ResourceLoader` 인터페이스를 통해 URL 및 파일과 같은 리소스에 액세스할 수 있다.
- 이벤트 퍼블리싱, 즉 `ApplicationListener` 인터페이스를 구현하는 빈에 `ApplicationEventPublisher` 인터페이스를 사용하여 퍼블리싱할 수 있다.
- 여러 (계층적) 컨텍스트를 로드하여 각각 애플리케이션의 웹 레이어와 같은 특정 레이어에 집중할 수 있도록 `HierarchicalBeanFactory` 인터페이스를 통해 설정할 수 있다.

##   `MessageSource`를 사용한 국제화

`ApplicationContext` 인터페이스는 `MessageSource`라는 인터페이스를 확장하므로 국제화("i18n") 기능을 제공한다. 또한 스프링은 메시지를 계층적으로 해결할 수 있는 `HierarchicalMessageSource` 인터페이스도 제공한다. 이러한 인터페이스는 함께 스프링이 메시지 해결에 영향을 미치는 기반을 제공한다. 이러한 인터페이스에 정의된 메서드는 다음과 같다.

- `String getMessage(String code, Object[] args, String default, Locale loc)`: `MessageSource`에서 메시지를 검색하는 데 사용되는 기본 메서드. 지정된 로캘에 대한 메시지를 찾을 수 없으면 기본 메시지가 사용된다. 전달된 모든 인수는 표준 라이브러리에서 제공하는 `MessageFormat` 기능을 사용하여 대체 값이 된다.
- `String getMessage(String code, Object[] args, Locale loc)`: 본질적으로 이전 메서드와 동일하지만 한 가지 차이점이 있다. 기본 메시지를 지정할 수 없다. 메시지를 찾을 수 없으면 `NoSuchMessageException`이 발생한다.
- `String getMessage(MessageSourceResolvable resolvable, Locale locale)`: 앞의 메서드에서 사용된 모든 속성은 이 메서드와 함께 사용할 수 있는 `MessageSourceResolvable`이라는 클래스로 래핑된다.

`ApplicationContext`가 로드되면 컨텍스트에 정의된 `MessageSource` 빈을 자동으로 검색한다. 빈의 이름은 `messageSource`여야 한다. 이러한 빈이 발견되면 앞의 메서드에 대한 모든 호출이 메시지 소스로 위임된다. 메시지 소스를 찾을 수 없으면 `ApplicationContext`는 같은 이름의 빈을 포함하는 부모를 찾으려고 시도한다. 찾으면 해당 빈을 `MessageSource`로 사용한다. `ApplicationContext`가 메시지 소스를 찾을 수 없는 경우, 위에 정의된 메서드에 대한 호출을 수락할 수 있도록 비어있는 `DelegatingMessageSource`가 인스턴스화된다.

스프링은 세 가지 `MessageSource` 구현체, `ResourceBundleMessageSource`, `ReloadableResourceBundleMessageSource` 및 `StaticMessageSource`를 제공한다. 이들 모두는 중첩된 메시징을 수행하기 위해 `HierarchicalMessageSource`를 구현한다. `StaticMessageSource`는 거의 사용되지 않지만 소스에 메시지를 추가하는 프로그래밍 방식을 제공한다. 다음 예시는 `ResourceBundleMessageSource`를 보여준다.

```xml
<beans>
    <bean id="messageSource"
            class="org.springframework.context.support.ResourceBundleMessageSource">
	<property name="basenames">
	    <list>
		<value>format</value>
		<value>exceptions</value>
		<value>windows</value>
	    </list>
	</property>
    </bean>
</beans>
```

이 예시에서는 클래스 경로에 `format`, `exceptions` 및 `windows`라는 세 가지 리소스 번들이 정의되어 있다고 가정한다. 메시지 해결 요청은 `ResourceBundle` 객체를 통해 메시지를 확인하는 JDK 표준 방식으로 처리된다. 이 예시에서는 위의 리소스 번들 파일 중 두 개의 내용이 다음과 같다고 가정한다.

```properties
# in format.properties
message=Alligators rock!
```

```properties
# in exceptions.properties
argument.required=The {0} argument is required.
```

다음 예시는 `MessageSource` 기능을 실행하는 프로그램을 보여준다. 모든 `ApplicationContext` 구현체는 `MessageSource` 구현체이기도 하므로 `MessageSource` 인터페이스로 캐스팅할 수 있다.

```java
public static void main(String[] args) {
    MessageSource resources = new ClassPathXmlApplicationContext("beans.xml");
    String message = resources.getMessage("message", null, "Default", Locale.ENGLISH);
    System.out.println(message);
}
```

위 프로그램의 결과 출력은 다음과 같다.

```
Alligators rock!
```

요약하자면, `MessageSource`는 클래스패스의 루트에 있는 `beans.xml`이라는 파일에 정의되어 있다. `messageSource` 빈 정의는 `basenames` 속성을 통해 여러 리소스 번들을 참조한다. 목록에서 `basenames` 속성으로 전달되는 세 개의 파일은 클래스 경로의 루트에 파일로 존재하며 각각 `format.properties`, `exceptions.properties` 및 `windows.properties`라고 한다.

다음 예시는 메시지 조회에 전달되는 인수를 보여준다. 이러한 인수는 `String` 객체로 변환되어 조회 메시지의 플레이스홀더에 삽입된다.

```xml
<beans>

    <!-- 이 메시지 소스가 웹 애플리케이션에서 사용 중이다 -->
    <bean id="messageSource" class="org.springframework.context.support.ResourceBundleMessageSource">
	<property name="basename" value="exceptions"/>
    </bean>

    <!-- 위의 MessageSource를 이 POJO에 주입할 수 있다 -->
    <bean id="example" class="com.something.Example">
	<property name="messages" ref="messageSource"/>
    </bean>

</beans>
```

```java
public class Example {

    private MessageSource messages;

    public void setMessages(MessageSource messages) {
	this.messages = messages;
    }

    public void execute() {
	String message = this.messages.getMessage("argument.required",
	    new Object [] {"userDao"}, "Required", Locale.ENGLISH);
	System.out.println(message);
    }
}
```

`execute()` 메서드 호출의 결과 출력은 다음과 같다.

```
The userDao argument is required.
```

국제화(“i18n”)와 관련하여 스프링의 다양한 `MessageSource` 구현은 표준 JDK `ResourceBundle`과 동일한 로캘 해결 및 폴백 규칙을 따른다. 간단히 말해, 앞서 정의한 메시지 소스 예제를 계속 이어서 영국(`en-GB`) 로캘에 대해 메시지를 확인하려는 경우, 각각 `format_en_GB.properties`, `exceptions_en_GB.properties` 및 `windows_en_GB.properties`라는 파일을 생성한다.

일반적으로 로캘 해결은 애플리케이션의 주변 환경에 의해 관리된다. 다음 예시에서는 (영국) 메시지가 해결되는 로캘을 수동으로 지정한다.

```
# in exceptions_en_GB.properties
argument.required=Ebagum lad, the ''{0}'' argument is required, I say, required.
```

```java
public static void main(final String[] args) {
    MessageSource resources = new ClassPathXmlApplicationContext("beans.xml");
    String message = resources.getMessage("argument.required",
	new Object [] {"userDao"}, "Required", Locale.UK);
    System.out.println(message);
}
```

위 프로그램을 실행한 결과 출력은 다음과 같다.

```
Ebagum lad, the 'userDao' argument is required, I say, required.
```

`MessageSourceAware` 인터페이스를 사용하여 정의된 모든 `MessageSource`에 대한 참조를 얻을 수도 있다. `MessageSourceAware` 인터페이스를 구현하는 `ApplicationContext`에 정의된 모든 빈은 빈이 생성 및 설정될 때 애플리케이션 컨텍스트의 `MessageSource`와 함께 주입된다.

> ### 주의
> 
> 스프링의 `MessageSource`는 자바의 `ResourceBundle`을 기반으로 하므로 기본 이름이 같은 번들을 병합하지 않고 발견된 첫 번째 번들만 사용한다. 기본 이름이 같은 후속 메시지 번들은 무시된다.

> ### 주의
> 
> `ResourceBundleMessageSource`의 대안으로 스프링은 `ReloadableResourceBundleMessageSource` 클래스를 제공한다. 이 변형은 동일한 번들 파일 형식을 지원하지만 표준 JDK 기반 `ResourceBundleMessageSource` 구현체보다 더 유연하다. 특히, 클래스패스뿐만 아니라 모든 스프링 리소스 위치에서 파일을 읽을 수 있으며, 번들 속성 파일의 핫 리로드를 지원하면서 그 사이에 효율적으로 캐싱할 수 있다. 자세한 내용은 [`ReloadableResourceBundleMessageSource`](https://docs.spring.io/spring-framework/docs/6.1.11/javadoc-api/org/springframework/context/support/ReloadableResourceBundleMessageSource.html) 자바독을 참조하라.

## 표준 및 사용자 정의 이벤트

`ApplicationContext`의 이벤트 처리는 `ApplicationEvent` 클래스와 `ApplicationListener` 인터페이스를 통해 제공된다. `ApplicationListener` 인터페이스를 구현하는 빈이 컨텍스트에 배포되면 `ApplicationEvent`가 `ApplicationContext`에 퍼블리싱될 때마다 해당 빈이 알림을 받는다. 기본적으로 이것은 표준 옵저버 디자인 패턴이다.

> ### 팁
> 
> 스프링 4.2부터 이벤트 인프라가 크게 개선되어 어노테이션 기반 모델과 임의의 이벤트(즉, `ApplicationEvent`에서 반드시 확장되지 않는 객체)를 퍼블리싱할 수 있는 기능을 제공한다. 이러한 객체가 퍼블리싱되면 해당 객체를 이벤트에 래핑한다.

다음 표는 스프링이 제공하는 표준 이벤트에 대해 설명한다.

| 이벤트                          | 설명                                                                                                                                                                                                                                                                                                                                                                                                        |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ContextRefreshedEvent`      | `ApplicationContext`가 초기화되거나 리프레시될 때(예를 들어, `ConfigurableApplicationContext` 인터페이스의 `refresh()` 메서드 사용) 퍼블리싱된다. 여기서 “초기화”는 모든 빈이 로드되고, 후처리기 빈이 감지 및 활성화되고, 싱글톤이 사전 인스턴스화되고, `ApplicationContext` 객체를 사용할 준비가 되었음을 의미한다. 컨텍스트가 닫히지 않은 한, 선택한 `ApplicationContext`가 실제로 이러한 “핫” 리프레시를 지원하는 경우 리프레시를 여러 번 트리거할 수 있다. 예를 들어, `XmlWebApplicationContext`는 핫 리프레시를 지원하지만 `GenericApplicationContext`는 지원하지 않는다. |
| `ContextStartedEvent`        | `ConfigurableApplicationContext` 인터페이스의 `start()` 메서드를 사용하여 `ApplicationContext`가 시작될 때 퍼블리싱된다. 여기서 “시작”이란 모든 `Lifecycle` 빈이 명시적 시작 신호를 수신한다는 의미이다. 일반적으로 이 신호는 명시적 중지 후 빈을 다시 시작하는 데 사용되지만, 자동 시작을 위해 설정되지 않은 구성 요소(예를 들어, 초기화 시 아직 시작되지 않은 구성 요소)를 시작하는 데도 사용될 수 있다.                                                                                                                                    |
| `ContextStoppedEvent`        | `ConfigurableApplicationContext` 인터페이스의 `stop()` 메서드를 사용하여 `ApplicationContext`가 중지될 때 퍼블리싱된다. 여기서 “중지”는 모든 `Lifecycle` 빈이 명시적인 중지 신호를 수신한다는 의미이다. 중지된 컨텍스트는 `start()` 호출을 통해 다시 시작할 수 있다.                                                                                                                                                                                                                |
| `ContextClosedEvent`         | `ConfigurableApplicationContext` 인터페이스의 `close()` 메서드를 사용하거나 JVM 종료 훅을 통해 `ApplicationContext`가 닫힐 때 퍼블리싱된다. 여기서 “닫힘”은 모든 싱글톤 빈이 소멸됨을 의미한다. 컨텍스트가 닫히면 수명이 다한 것이므로 리프레시하거나 다시 시작할 수 없다.                                                                                                                                                                                                                    |
| `RequestHandledEvent`        | 모든 빈에 HTTP 요청이 처리되었음을 알리는 웹 전용 이벤트이다. 이 이벤트는 요청이 완료된 후에 퍼블리싱된다. 이 이벤트는 스프링의 `DispatcherServlet`을 사용하는 웹 애플리케이션에만 적용된다.                                                                                                                                                                                                                                                                                    |
| `ServletRequestHandledEvent` | 서블릿 관련 컨텍스트 정보를 추가하는 `RequestHandledEvent`의 서브클래스이다.                                                                                                                                                                                                                                                                                                                                                      |
사용자 정의 이벤트를 직접 생성하고 퍼블리싱할 수도 있다. 다음 예시는 스프링의 `ApplicationEvent` 기본 클래스를 확장하는 간단한 클래스를 보여준다.

```java
public class BlockedListEvent extends ApplicationEvent {

    private final String address;
    private final String content;

    public BlockedListEvent(Object source, String address, String content) {
	super(source);
	this.address = address;
	this.content = content;
    }

    // 접근자 및 다른 메서드...
}
```

사용자 정의 `ApplicationEvent`를 퍼블리싱하려면 `ApplicationEventPublisher`에서 `publishEvent()` 메서드를 호출한다. 일반적으로 이 작업은 `ApplicationEventPublisherAware`를 구현하는 클래스를 생성하고 스프링 빈으로 등록하여 수행한다. 다음 예시는 이러한 클래스를 보여준다.

```java
public class EmailService implements ApplicationEventPublisherAware {

    private List<String> blockedList;
    private ApplicationEventPublisher publisher;

    public void setBlockedList(List<String> blockedList) {
	this.blockedList = blockedList;
    }

    public void setApplicationEventPublisher(ApplicationEventPublisher publisher) {
	this.publisher = publisher;
    }

    public void sendEmail(String address, String content) {
	if (blockedList.contains(address)) {
	    publisher.publishEvent(new BlockedListEvent(this, address, content));
	    return;
	}
	// 이메일 전송...
    }
}
```

설정 시 스프링 컨테이너는 `EmailService`가 `ApplicationEventPublisherAware`를 구현하는 것을 감지하고 자동으로 `setApplicationEventPublisher()`를 호출한다. 실제로 전달되는 매개 변수는 스프링 컨테이너 자체이다. 애플리케이션 컨텍스트와 상호작용하는 것은 애플리케이션`EventPublisher` 인터페이스를 통해 이루어진다.

사용자 정의 `ApplicationEvent`를 수신하려면, `ApplicationListener`를 구현하는 클래스를 생성하고 스프링 빈으로 등록하면 된다. 다음 예시는 이러한 클래스를 보여준다.

```java
public class BlockedListNotifier implements ApplicationListener<BlockedListEvent> {

    private String notificationAddress;

    public void setNotificationAddress(String notificationAddress) {
	this.notificationAddress = notificationAddress;
    }

    public void onApplicationEvent(BlockedListEvent event) {
	// notificationAddress를 통해 적절한 당사자에게 알림...
    }
}
```

`ApplicationListener`는 일반적으로 사용자 정의 이벤트 유형(앞의 예시에서는 `BlockedListEvent`)으로 매개변수화되어 있다. 즉, `onApplicationEvent()` 메서드는 타입 안전성을 유지할 수 있으므로 다운캐스팅이 필요하지 않다. 이벤트 리스너는 원하는 만큼 등록할 수 있지만 기본적으로 이벤트 리스너는 이벤트를 동기식으로 수신한다는 점에 유의하라. 즉, 모든 리스너가 이벤트 처리를 완료할 때까지 `publishEvent()` 메서드가 차단된다. 이 동기식 단일 스레드 접근 방식의 한 가지 장점은, 리스너가 이벤트를 수신할 때 트랜잭션 컨텍스트를 사용할 수 있는 경우 퍼블리셔의 트랜잭션 컨텍스트 내에서 작동한다는 것이다. 이벤트 퍼블리싱을 위한 다른 전략(예를 들어, 기본적으로 비동기 이벤트 처리)이 필요한 경우, 사용자 정의 “`applicationEventMulticaster`” 빈 정의에 적용할 수 있는 설정 옵션은 스프링의 [`ApplicationEventMulticaster`](https://docs.spring.io/spring-framework/docs/6.1.11/javadoc-api/org/springframework/context/event/ApplicationEventMulticaster.html) 인터페이스 및 [`SimpleApplicationEventMulticaster`](https://docs.spring.io/spring-framework/docs/6.1.11/javadoc-api/org/springframework/context/event/SimpleApplicationEventMulticaster.html) 구현체에 대한 자바독을 참조하라. 이러한 경우 이벤트 처리를 위해 ThreadLocals 및 로깅 컨텍스트가 전파되지 않는다. 옵저버빌리티 문제에 대한 자세한 내용은 @EventListener 옵저버빌리티 섹션을 참조하라.

다음 예는 위의 각 클래스를 등록하고 설정하는 데 사용된 빈 정의를 보여준다.

```xml
<bean id="emailService" class="example.EmailService">
    <property name="blockedList">
	<list>
	    <value>known.spammer@example.org</value>
	    <value>known.hacker@example.org</value>
	    <value>john.doe@example.org</value>
	</list>
    </property>
</bean>

<bean id="blockedListNotifier" class="example.BlockedListNotifier">
    <property name="notificationAddress" value="blockedlist@example.org"/>
</bean>

   <!-- 옵션: 사용자 정의 ApplicationEventMulticaster 정의 -->
<bean id="applicationEventMulticaster" class="org.springframework.context.event.SimpleApplicationEventMulticaster">
    <property name="taskExecutor" ref="..."/>
    <property name="errorHandler" ref="..."/>
</bean>
```

이 모든 것을 종합하면, `emailService` 빈의 `sendEmail()` 메서드가 호출될 때 차단해야 하는 이메일 메시지가 있는 경우, `BlockedListEvent` 타입의 사용자 정의 이벤트가 퍼블리싱된다. `blockedListNotifier` 빈은 `ApplicationListener`로 등록되고 `BlockedListEvent`를 수신하며, 이 시점에서 적절한 당사자에게 알릴 수 있다.

> ### 주의
> 
> 스프링의 이벤트 메커니즘은 동일한 애플리케이션 컨텍스트 내에서 스프링 빈 간의 간단한 통신을 위해 설계되었다. 그러나 보다 정교한 엔터프라이즈 통합이 필요한 경우, 별도로 유지 관리되는 [스프링 통합](https://spring.io/projects/spring-integration) 프로젝트는 잘 알려진 스프링 프로그래밍 모델을 기반으로 하는 경량, [패턴 지향](https://www.enterpriseintegrationpatterns.com/), 이벤트 중심 아키텍처를 구축하는 데 완벽한 지원을 제공한다.

### 어노테이션 기반 이벤트 리스너

`@EventListener` 어노테이션을 사용하여 관리되는 빈의 모든 메서드에 이벤트 리스너를 등록할 수 있다. `BlockedListNotifier`는 다음과 같이 재작성할 수 있다.

```java
public class BlockedListNotifier {

    private String notificationAddress;

    public void setNotificationAddress(String notificationAddress) {
	this.notificationAddress = notificationAddress;
    }

    @EventListener
    public void processBlockedListEvent(BlockedListEvent event) {
	// notificationAddress를 통해 적절한 당사자에게 알림...
    }
}
```

메서드 시그니처는 수신하는 이벤트 타입을 다시 한번 선언하지만, 이번에는 특정 리스너 인터페이스를 구현하지 않고 유연한 이름으로 선언한다. 실제 이벤트 타입이 구현 계층 구조에서 제네릭 매개변수를 해결하는 한 이벤트 타입은 제네릭을 통해 좁혀질 수도 있다.

메서드가 여러 이벤트를 수신해야 하거나 매개변수 없이 정의하려는 경우, 이벤트 타입을 어노테이션 자체에 지정할 수도 있다. 다음 예시는 그 방법을 보여준다.

```java
@EventListener({ContextStartedEvent.class, ContextRefreshedEvent.class})
public void handleContextStart() {
    // ...
}
```

특정 이벤트에 대한 메서드를 실제로 호출하려면 일치해야 하는 [`SpEL` 표현식](https://docs.spring.io/spring-framework/reference/core/expressions.html)을 정의하는 어노테이션의 `condition` 속성을 사용하여 추가적인 런타임 필터링을 추가할 수도 있다.

다음 예시는 이벤트의 `content` 속성이 `my-event`와 같은 경우에만 호출되도록 알림을 재작성하는 방법을 보여준다.

```java
@EventListener(condition = "#blEvent.content == 'my-event'")
public void processBlockedListEvent(BlockedListEvent blEvent) {
    // notificationAddress를 통해 적절한 당사자에게 알림...
}
```

각 `SpEL` 표현식은 전용 컨텍스트에 대해 평가된다. 다음 표에는 조건부 이벤트 처리에 사용할 수 있도록 컨텍스트에서 사용할 수 있는 항목이 나열되어 있다.

| 이름              | 위치      | 설명                                                                                                                                                  | 예시                                                                 |
| --------------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Event           | 루트 객체   | 실제 `ApplicationEvent`.                                                                                                                              | `#root.event` or `event`                                           |
| Arguments array | 루트 객체   | 메서드를 호출하는 데 사용되는 인자(객체 배열)이다.                                                                                                                       | `#root.args` 또는 `args`; `args[0]`을 사용하여 첫 번째 인수 등에 액세스합니다.         |
| Argument name   | 평가 컨텍스트 | 메서드 인자의 이름이다. 어떤 이유로 이름을 사용할 수 없는 경우(예를 들어, 컴파일된 바이트 코드에 디버그 정보가 없기 때문), 개별 인수는 `#a<#arg>` 구문을 사용하여 사용할 수도 있으며, 여기서 `<#arg>`는 인수 인덱스(0부터 시작)를 나타낸다. | `#blEvent` 또는 `#a0`(`#p0` 또는 `#p<#arg>` 매개변수 표기법을 별칭으로 사용할 수도 있다.) |
메서드 시그니처가 실제로 퍼블리싱된 임의의 객체를 참조하더라도,  `#root.event`를 사용하면 기본 이벤트에 액세스할 수 있다는 점에 유의하라.

다른 이벤트를 처리한 결과로 이벤트를 퍼블리싱해야 하는 경우 다음 예시와 같이 메서드 시그니처를 변경하여 퍼블리싱해야 하는 이벤트를 반환할 수 있다.

```java
@EventListener
public ListUpdateEvent handleBlockedListEvent(BlockedListEvent event) {
    // notificationAddress를 통해 적절한 당사자에게 알린 다음
    // ListUpdateEvent를 퍼블리싱한다...
}
```

> ### 주의
> 
> 이 기능은 비동기식 리스너에는 지원되지 않는다.

`handleBlockedListEvent()` 메서드는 처리하는 모든 `BlockedListEvent`에 대해 새로운 `ListUpdateEvent`를 퍼블리싱한다. 여러 이벤트를 퍼블리싱해야 하는 경우 `Collection`이나 이벤트 배열을 대신 반환할 수 있다.

### 비동기 리스너

특정 리스너가 이벤트를 비동기적으로 처리하도록 하려면 일반 @Async 지원을 재사용할 수 있다. 다음 예시는 그 방법을 보여준다.

```java
@EventListener
@Async
public void processBlockedListEvent(BlockedListEvent event) {
    // BlockedListEvent는 별도의 스레드에서 처리된다
}
```

비동기 이벤트를 사용할 때는 다음 제한 사항에 유의하라.

- 비동기 이벤트 리스너가 `Exception`을 던지면 호출자에게 전파되지 않는다. 자세한 내용은 [`AsyncUncaughtExceptionHandler`](https://docs.spring.io/spring-framework/docs/6.1.11/javadoc-api/org/springframework/aop/interceptor/AsyncUncaughtExceptionHandler.html)를 참조하라.
- 비동기 이벤트 리스너 메서드는 값을 반환하여 후속 이벤트를 퍼블리싱할 수 없다. 처리 결과로 다른 이벤트를 퍼블리싱해야 하는 경우 [`ApplicationEventPublisher`](https://docs.spring.io/spring-framework/docs/6.1.11/javadoc-api/org/springframework/context/ApplicationEventPublisher.html)를 삽입하여 수동으로 이벤트를 퍼블리싱하라.
- 스레드 로컬과 로깅 컨텍스트는 이벤트 처리를 위해 기본적으로 전파되지 않는다. 가관측성 문제에 대한 자세한 내용은 `@EventListener` 가관측성 섹션을 참조하라.

### 리스너 순서 정하기

하나의 리스너가 다른 리스너보다 먼저 호출되어야 하는 경우, 다음 예시처럼 메서드 선언에 `@Order` 어노테이션을 추가할 수 있다.

```java
@EventListener
@Order(42)
public void processBlockedListEvent(BlockedListEvent event) {
    // notificationAddress를 통해 적절한 당사자에게 알림...
}
```

### 제네릭 이벤트

제네릭을 사용하여 이벤트의 구조를 추가로 정의할 수도 있다. `EntityCreatedEvent<T>`(여기서 `T`는 실제 생성된 엔티티의 유형이다)를 사용하는 것을 고려해 보라. 예를 들어, 다음과 같은 리스너 정의를 만들어 `Person`에 대한 `EntityCreatedEvent`만 수신할 수 있다.

```java
@EventListener
public void onPersonCreated(EntityCreatedEvent<Person> event) {
    // ...
}
```

타입 소거 때문에, 이 방법은 이벤트 리스너가 필터링하는 제네릭 매개변수를 이벤트가 해결할 때만 작동한다(예를 들어, `PersonCreatedEvent` 클래스가 `EntityCreatedEvent<Person>`를 확장하는 경우와 같다).

특정 상황에서는 모든 이벤트가 동일한 구조를 따르는 경우(앞의 예제에서 이벤트의 경우처럼) 이 작업이 상당히 지루해질 수 있다. 이러한 경우 `ResolvableTypeProvider`를 구현하여 런타임 환경이 제공하는 것 이상으로 프레임워크를 가이드할 수 있다. 다음 이벤트는 그 방법을 보여준다.

```java
public class EntityCreatedEvent<T> extends ApplicationEvent implements ResolvableTypeProvider {

    public EntityCreatedEvent(T entity) {
	super(entity);
    }

    @Override
    public ResolvableType getResolvableType() {
	return ResolvableType.forClassWithGenerics(getClass(), ResolvableType.forInstance(getSource()));
    }
}
```

> ### 팁
> 
> 이는 `ApplicationEvent`뿐만 아니라 이벤트로 전송하는 임의의 객체에서도 작동한다.

마지막으로, 기존 `ApplicationListener` 구현과 마찬가지로 실제 멀티캐스팅은 런타임에 컨텍스트 전체 `ApplicationEventMulticaster`를 통해 이루어진다. 기본적으로 이것은 호출자 스레드에 동기식 이벤트 퍼블리싱이 있는 `SimpleApplicationEventMulticaster`이다. 모든 이벤트를 비동기적으로 처리하거나 리스너 예외를 처리하는 등의 경우 “`applicationEventMulticaster`” 빈 정의를 통해 이를 대체/사용자 정의할 수 있다.

```java
@Bean
ApplicationEventMulticaster applicationEventMulticaster() {
    SimpleApplicationEventMulticaster multicaster = new SimpleApplicationEventMulticaster();
    multicaster.setTaskExecutor(...);
    multicaster.setErrorHandler(...);
    return multicaster;
}
```

## 저수준 리소스에 대한 편리한 액세스

애플리케이션 컨텍스트를 최적으로 사용하고 이해하려면 리소스에 설명된 대로 스프링의 `Resource` 추상화에 익숙해져야 한다.

애플리케이션 컨텍스트는 `Resource` 객체를 로드하는 데 사용할 수 있는 `ResourceLoader`이다. `Resource`는 기본적으로 JDK `java.net.URL` 클래스의 기능이 더 풍부한 버전이다. 실제로 Resource의 구현은 적절한 경우 `java.net.URL`의 인스턴스를 래핑한다. `Resource`는 클래스패스, 파일 시스템 위치, 표준 URL로 설명할 수 있는 모든 위치 및 기타 변형을 포함하여 거의 모든 위치에서 투명한 방식으로 저수준 리소스를 가져올 수 있다. 리소스 위치 문자열이 특별한 접두사가 없는 단순한 경로인 경우, 해당 리소스의 출처는 실제 애플리케이션 컨텍스트 타입에 따라 구체적이고 적절하다.

빈을 애플리케이션 컨텍스트에 배포할 때, 특별한 콜백 인터페이스인 `ResourceLoaderAware`를 구현하도록 구성할 수 있으며, 초기화 시 애플리케이션 컨텍스트가 `ResourceLoader`로 전달되어 자동으로 호출된다. 또한 정적 리소스에 액세스하는 데 사용되는 `Resource` 타입의 속성을 노출할 수도 있다. 이러한 속성은 다른 속성과 마찬가지로 주입된다. 이러한 `Resource` 속성을 간단한 `String` 경로로 지정하고 빈이 배포될 때 해당 텍스트 문자열을 실제 `Resource` 객체로 자동 변환할 수 있다.

`ApplicationContext` 생성자에 제공된 위치 경로는 실제로는 리소스 문자열이며, 간단한 형식으로 특정 컨텍스트 구현에 따라 적절하게 처리된다. 예를 들어 `ClassPathXmlApplicationContext`는 단순한 위치 경로를 클래스패스 위치로 취급한다. 또한 특수 접두사와 함께 위치 경로(리소스 문자열)를 사용하여 실제 컨텍스트 타입에 관계없이 클래스패스 또는 URL에서 정의를 강제로 로드할 수도 있다.

## 애플리케이션 시작 추적

`ApplicationContext`는 스프링 애플리케이션의 라이프사이클을 관리하고 컴포넌트를 중심으로 풍부한 프로그래밍 모델을 제공한다. 따라서 복잡한 애플리케이션도 똑같이 복잡한 컴포넌트 그래프와 시작 단계를 가질 수 있다.

특정 메트릭으로 애플리케이션 시작 단계를 추적하면 시작 단계에서 시간이 어디에 소비되고 있는지 파악하는 데 도움이 될 뿐만 아니라 컨텍스트 라이프사이클 전체를 더 잘 이해하는 방법으로도 사용할 수 있다.

`AbstractApplicationContext`(및 그 하위 클래스)는 다양한 시작 단계에 대한 `StartupStep` 데이터를 수집하는 `ApplicationStartup`으로 관찰된다.

- 애플리케이션 컨텍스트 라이프사이클(기본 패키지 스캔, 설정 클래스 관리)
- 빈 라이프사이클(인스턴스화, 스마트 초기화, 후처리)
- 애플리케이션 이벤트 처리

다음은 `AnnotationConfigApplicationContext`의 관찰 예시이다.

```java
// 시작 단계를 만들고 기록을 시작한다
StartupStep scanPackages = getApplicationStartup().start("spring.context.base-packages.scan");
// 현재 단계에 태그 정보를 추가한다
scanPackages.tag("packages", () -> Arrays.toString(basePackages));
// 관찰하는 실제 단계를 수행한다
this.scanner.scan(basePackages);
// 현재 단계를 끝낸다
scanPackages.end();
```

애플리케이션 컨텍스트는 이미 여러 단계로 관찰되어 있다. 일단 기록되면 이러한 시작 단계는 특정 도구를 사용하여 수집, 표시 및 분석할 수 있다. 기존 시작 단계의 전체 목록은 [전용 부록 섹션](https://docs.spring.io/spring-framework/reference/core/appendix/application-startup-steps.html)에서 확인할 수 있다.

기본 `ApplicationStartup` 구현체는 오버헤드를 최소화하기 위해 연산이 없는 변형이다. 즉, 애플리케이션을 시작하는 동안 기본적으로 메트릭이 수집되지 않는다. 스프링 프레임워크에는 Java Flight Recorder로 시작 단계를 추적하기 위한 `FlightRecorderApplicationStartup` 구현체가 함께 제공된다. 이 변형을 사용하려면 인스턴스가 생성되는 즉시 해당 인스턴스를 `ApplicationContext`로 설정해야 한다.

개발자는 자체 `AbstractApplicationContext` 서브클래스를 제공하거나 보다 정확한 데이터를 수집하려는 경우 `ApplicationStartup` 인프라를 사용할 수도 있다.

> ### 경고
> 
> `ApplicationStartup`은 애플리케이션을 시작할 때와 코어 컨테이너에만 사용되며, 자바 프로파일러나 Micrometer와 같은 메트릭 라이브러리를 대체할 수 있는 것은 결코 아니다.

컴포넌트는 사용자 정의 `StartupStep` 수집을 시작하기 위해 애플리케이션 컨텍스트에서 직접 `ApplicationStartup` 인스턴스를 가져오거나, 컴포넌트가 `ApplicationStartupAware`를 구현하도록 하거나, 모든 주입 지점에서 `ApplicationStartup` 타입을 요청할 수 있다.

> ### 주의
> 
> 개발자는 사용자 정의 시작 단계를 만들 때 `“spring.*”` 네임스페이스를 사용해서는 안 된다. 이 네임스페이스는 내부 스프링 사용을 위해 예약되어 있으며 변경될 수 있다.

## 웹 애플리케이션을 위한 편리한 애플리케이션컨텍스트 인스턴스화

예를 들어 `ContextLoader`를 사용하여 선언적으로 `ApplicationContext` 인스턴스를 생성할 수 있다. 물론 `ApplicationContext` 구현체 중 하나를 사용하여 프로그래밍 방식으로 `ApplicationContext` 인스턴스를 생성할 수도 있다.

다음 예시와 같이 `ContextLoaderListener`를 사용하여 `ApplicationContext`를 등록할 수 있다.

```xml
<context-param>
    <param-name>contextConfigLocation</param-name>
    <param-value>/WEB-INF/daoContext.xml /WEB-INF/applicationContext.xml</param-value>
</context-param>

<listener>
    <listener-class>org.springframework.web.context.ContextLoaderListener</listener-class>
</listener>
```

리스너는 `contextConfigLocation` 매개변수를 검사한다. 매개변수가 존재하지 않으면 리스너는 `/WEB-INF/applicationContext.xml`을 기본값으로 사용한다. 매개변수가 존재하면 수신기는 미리 정의된 구분 기호(쉼표, 세미콜론, 공백)를 사용하여 `String`을 구분하고 해당 값을 애플리케이션 컨텍스트가 검색되는 위치로 사용한다. Ant 스타일 경로 패턴도 지원된다. 예를 들어 `/WEB-INF/*Context.xml`(이름이 `Context.xml`로 끝나고 `WEB-INF` 디렉터리에 있는 모든 파일) 및 `/WEB-INF/**/*Context.xml`(`WEB-INF`의 하위 디렉터리에 있는 모든 파일)이 있다.

## 스프링 `ApplicationContext`를 자카르타 EE RAR 파일로 배포하기

스프링 `ApplicationContext`를 RAR 파일로 배포하여 컨텍스트와 필요한 모든 빈 클래스 및 라이브러리 JAR을 자카르타 EE RAR 배포 유닛에 캡슐화할 수 있다. 이는 독립형 `ApplicationContext`(자카르타 EE 환경에서만 호스팅됨)를 부트스트랩하여 자카르타 EE 서버 시설에 액세스할 수 있도록 하는 것과 같다. RAR 배포는 헤드리스 WAR 파일을 배포하는 시나리오에 대한 더 자연스러운 대안이다. 헤드리스 WAR 파일은 HTTP 진입점 없는 WAR 파일로, 자카르타 EE 환경에서 스프링 `ApplicationContext`를 부트스트랩하는 데만 사용된다.

RAR 배포는 HTTP 진입점이 필요하지 않고 메시지 엔드포인트와 예약된 작업으로만 구성된 애플리케이션 컨텍스트에 이상적이다. 이러한 컨텍스트의 빈은 JTA 트랜잭션 관리자, JNDI에 바인딩된 JDBC `DataSource` 인스턴스 및 JMS `ConnectionFactory` 인스턴스와 같은 애플리케이션 서버 리소스를 사용할 수 있으며, 스프링의 표준 트랜잭션 관리 및 JNDI와 JMX 지원 기능을 통해 플랫폼의 JMX 서버에 등록할 수도 있다. 또한 애플리케이션 컴포넌트는 스프링의 `TaskExecutor` 추상화를 통해 애플리케이션 서버의 JCA `WorkManager`와 상호 작용할 수 있다.

RAR 배포와 관련된 설정 세부 사항은 `SpringContextResourceAdapter` 클래스의 자바독을 참조하라.

스프링 ApplicationContext를 자카르타 EE RAR 파일로 간단하게 배포할 수 있다.

1. 모든 애플리케이션 클래스를 RAR 파일(파일 확장자가 다른 표준 JAR 파일)로 패키징한다.
2. 필요한 모든 라이브러리 JAR을 RAR 아카이브의 루트에 추가한다.
3. `SpringContextResourceAdapter`의 자바독에 표시된 것처럼 `META-INF/ra.xml` 배포 디스크립터와 해당 스프링 XML 빈 정의 파일(일반적으로 `META-INF/applicationContext.xml`)을 추가한다.
4. 결과물인 RAR 파일을 애플리케이션 서버의 배포 디렉토리에 드롭한다.

> ### 주의
> 
> 이러한 RAR 배포 유닛은 일반적으로 독립형이다. 구성 요소를 외부에 노출하지 않으며, 심지어 동일한 애플리케이션의 다른 모듈에도 노출하지 않는다. RAR 기반 `ApplicationContext`와의 상호 작용은 일반적으로 다른 모듈과 공유하는 JMS 대상을 통해 이루어진다. 예를 들어, RAR 기반 `ApplicationContext`는 일부 작업을 예약하거나 파일 시스템의 새 파일에 반응할 수도 있다. 외부에서 동기식 액세스를 허용해야 하는 경우, 예를 들어 동일한 컴퓨터의 다른 애플리케이션 모듈에서 사용할 수 있는 RMI 엔드포인트를 내보낼 수 있다.
