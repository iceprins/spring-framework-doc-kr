# 빈 팩토리 API

`BeanFactory` API는 스프링의 IoC 기능에 대한 기본 기반을 제공한다. 특정 컨트랙트는 주로 스프링의 다른 부분 및 관련 타사 프레임워크와의 통합에 사용되며, `DefaultListableBeanFactory` 구현체는 상위 수준 `GenericApplicationContext` 컨테이너 내의 핵심 델리게이트이다.

`BeanFactory` 및 관련 인터페이스(예를 들어 `BeanFactoryAware`, `InitializingBean`, `DisposableBean`)는 다른 프레임워크 구성 요소에 대한 중요한 통합 지점이다. 어노테이션이나 리플렉션이 필요하지 않기 때문에 컨테이너와 해당 구성 요소 간에 매우 효율적인 상호 작용이 가능하다. 애플리케이션 수준 빈은 동일한 콜백 인터페이스를 사용할 수 있지만, 일반적으로 어노테이션이나 프로그래밍 방식의 설정을 통해 선언적 의존성 주입을 선호한다.

`BeanFactory`의 핵심 API 수준과 그 구현체인 `DefaultListableBeanFactory`는 설정 형식이나 사용할 구성 요소 어노테이션에 대한 가정을 하지 않는다. 이러한 다양한 형태의 기능들은 `XmlBeanDefinitionReader`나 `AutowiredAnnotationBeanPostProcessor`와 같은 확장 기능을 통해 제공되며, 이들은 모두 핵심 메타데이터 표현으로써 공유되는 `BeanDefinition` 객체들에 대해 작동한다. 스프링의 컨테이너가 매우 유연하고 확장 가능한 본질은 바로 이 점에 있다.

## `BeanFactory`와 `ApplicationContext` 중에 무엇으로?

이 섹션에서는 `BeanFactory`와 `ApplicationContext` 컨테이너 수준 간의 차이점과 부트스트랩에 미치는 영향에 대해 설명한다.

특별한 이유가 없는 한 `ApplicationContext`를 사용해야 하며, `GenericApplicationContext`와 그 하위클래스인 `AnnotationConfigApplicationContext`가 사용자 정의 부트스트랩을 위한 일반적인 구현체이다. 이들은 설정 파일 로드, 클래스패스 스캔 트리거, 프로그래밍 방식으로 빈 정의 및 어노테이션이 달린 클래스 등록, 함수형 빈 정의 등록 등 모든 일반적인 목적의 스프링의 핵심 컨테이너에 대한 주요 진입점이다.

`ApplicationContext`는 `BeanFactory`의 모든 기능을 포함하므로, 빈 처리에 대한 완전한 제어가 필요한 시나리오를 제외하고는 일반적으로 일반 `BeanFactory`보다 권장된다. `ApplicationContext`(예를 들어 `GenericApplicationContext` 구현체) 내에서 여러 종류의 빈은 규칙(즉, 빈 이름 또는 빈 타입, 특히 후처리기)에 의해 감지되는 반면, 일반 `DefaultListableBeanFactory`는 특별한 빈에 대해 무관심하다.

어노테이션 처리 및 AOP 프록시와 같은 많은 확장 컨테이너 기능의 경우 [`BeanPostProcessor` 확장 포인트](https://github.com/iceprins/spring-framework-doc-kr/blob/main/1.%20IoC%20%EC%BB%A8%ED%85%8C%EC%9D%B4%EB%84%88/8.%20%EC%BB%A8%ED%85%8C%EC%9D%B4%EB%84%88%20%ED%99%95%EC%9E%A5%20%ED%8F%AC%EC%9D%B8%ED%8A%B8.md#beanpostprocessor%EB%A5%BC-%EC%82%AC%EC%9A%A9%ED%95%98%EC%97%AC-%EB%B9%88-%EC%BB%A4%EC%8A%A4%ED%84%B0%EB%A7%88%EC%9D%B4%EC%A7%95)가 필수적이다. 일반 `DefaultListableBeanFactory`만 사용하는 경우, 이러한 후처리기는 기본적으로 감지 및 활성화되지 않는다. 이 상황은 실제로 빈 설정에 아무런 문제가 없기 때문에 혼란스러울 수 있다. 오히려 이러한 시나리오에서는 추가 설정을 통해 컨테이너를 완전히 부트스트랩해야 한다.

다음 표에는 `BeanFactory` 및 `ApplicationContext` 인터페이스와 구현체에서 제공하는 기능이 나열되어 있다.

| 특징                                | `BeanFactory` | `ApplicationContext` |
| --------------------------------- | ------------- | -------------------- |
| 빈 인스턴스화/연결                        | 네             | 네                    |
| 통합 라이프사이클 관리                      | 아니오           | 네                    |
| 자동 `BeanPostProcessor` 등록         | 아니오           | 네                    |
| 자동 `BeanFactoryPostProcessor` 등록  | 아니오           | 네                    |
| (국제화를 위한) 편리한 `MessageSource` 액세스 | 아니오           | 네                    |
| 내장 `ApplicationEvent` 퍼블리싱 메커니즘   | 아니오           | 네                    |
빈 후처리기를 명시적으로 `DefaultListableBeanFactory`에 등록하려면 다음 예시에서와 같이 프로그래밍 방식으로 `addBeanPostProcessor`를 호출해야 한다.

```java
DefaultListableBeanFactory factory = new DefaultListableBeanFactory();
// 빈 정의로 factory 채우기

// 이제 필요한 BeanPostProcessor 인스턴스를 등록한다
factory.addBeanPostProcessor(new AutowiredAnnotationBeanPostProcessor());
factory.addBeanPostProcessor(new MyBeanPostProcessor());

// 이제 팩토리 사용을 시작한다
```

`BeanFactoryPostProcessor`를 일반 `DefaultListableBeanFactory`에 적용하려면 다음 예시에서와 같이 해당 `postProcessBeanFactory` 메서드를 호출해야 한다.

```java
DefaultListableBeanFactory factory = new DefaultListableBeanFactory();
XmlBeanDefinitionReader reader = new XmlBeanDefinitionReader(factory);
reader.loadBeanDefinitions(new FileSystemResource("beans.xml"));

// 속성 파일에서 일부 속성 값을 가져온다
PropertySourcesPlaceholderConfigurer cfg = new PropertySourcesPlaceholderConfigurer();
cfg.setLocation(new FileSystemResource("jdbc.properties"));

// 이제 실제로 교체를 한다
cfg.postProcessBeanFactory(factory);
```

두 경우 모두 명시적인 등록 단계가 불편하기 때문에, 특히 일반적인 엔터프라이즈 환경에서 확장된 컨테이너 기능을 위해 `BeanFactoryPostProcessor`와 `BeanPostProcessor` 인스턴스에 의존하는 경우, 스프링 기반 애플리케이션에서는 단순한 `DefaultListableBeanFactory`보다 다양한 `ApplicationContext` 변형이 선호된다.

> ### 주의
> 
> `AnnotationConfigApplicationContext`에는 모든 일반적인 어노테이션 후처리기가 등록되어 있으며 `@EnableTransactionManagement`와 같은 설정 어노테이션을 통해 커버 아래에 추가 프로세서를 가져올 수 있다. 스프링의 어노테이션 기반 설정 모델의 추상화 수준에서 빈 후처리기의 개념은 단순한 내부 컨테이너 세부 사항에 불과하다.
